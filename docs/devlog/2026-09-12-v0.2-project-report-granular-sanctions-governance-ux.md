# 2026-09-12 · 项目举报、细分限制与治理入口整理

## 起因

前一轮治理只覆盖项目动态举报；网站人员无法从稳定用户 ID 查看完整处分历史，旧版「限制发布 / 限制账号」也无法准确表达评论、发项目、响应和全站停用的差别。公告草稿强制填写「起草依据」增加理解成本；授权记录与管理员入口分开，网站公告管理入口又与公共公告分离。用户希望先实现可配置功能，再共同制定违规分级、惩罚期限和管理细则。

## 本次具体修改

- `ProjectReport` 固化项目公开版本的标题、简介、描述、标签、发起人和举报说明，允许盗用作品、未经授权素材、虚假项目、误导标签、违规内容等类别。独立的网站举报审核员可维持公开或暂时下架；项目在「我的项目」与发起人详情留有下架回执，发起人可以向非原审查人的管理员或无利益冲突的站主申诉。下架、恢复和站主纠错不删除原决定，相关人员收到站内通知。相同项目并发举报统一按项目锁串行处理；下架时合并其他未处理举报；项目更新版本后必须再次确认当前内容才可下架。
- 账号处分范围增加 `COMMENTS`、`PROJECTS`、`RESPONSES`、`SITE`，保留已有 `POSTING`、`ACCOUNT` 历史值。不同局部限制可独立作出、申诉和撤销；同类限制与有效全站停用不得重叠。发项目及动态、响应和未来评论入口分别受服务端检查；最高级全站停用只可由站主作出永久处分并附原因，留本人处分页、消息和申诉入口以便纠错，不销毁用户账号或项目贡献。全站停用时顶部导航也仅指向账号状态和消息，避免无效跳转。旧处分仍按原效果继续生效，不擅自改写历史。
- 网站管理人员可按完整用户 ID、邮箱或名称查「用户治理记录」：列表以温和且可辨别的颜色和文字显示普通、一次已确认处置、多次已确认处置、目前受限、全站停用。同一项目或动态收到多条举报仅计一次，已确认的不当移出也计入治理记录；未核实举报和已撤销处分不算已确认违规。精确查找的详情保留历史处分、操作人、理由、申诉及处理事件，并列出已审结内容举报和平台同行移出复核，不泄露举报人未公开的陈述。
- 网站管理员与授权记录同页，旧日志网址安全跳转；普通公告页只对站主和授权公告管理员显示「起草、编辑与发布」按钮。草稿免填晦涩的「起草依据」；实际发布、撤回及公开公告修改要求填写仅供网站审核的说明，原草稿或公告正文保留历史快照。用户可见的理由、类别和操作状态统一中文，内部数据枚举仍保留英文稳定代码。
- 内容筛查规则页增加仅站主可调的「未命中则自动公开动态」策略，默认继续人工审核。开启时须填理由并确认误判风险，写策略事件；自动公开动态标出策略变更来源，仍接受举报、下架、申诉。词条规则命中 `REVIEW` 或 `BLOCK` 仍走原人工分流。

## 取舍与风险

不把涉嫌违规的举报当成当事人的「案底」；仅已作出且未撤销的处分和当前经审核下架的内容影响管理色阶。没有写「第几次违规必须封多久」的硬编码表，这是以后一起制定并公示的管理细则。评论还未有数据模型，`COMMENTS` 限制已经预留权限检查入口，等评论功能接入时才实际阻止评论或回复。词条未命中并不代表安全；自动公开是站主主动开启的风险选择，仍需持续记录举报和误判。

## 结构、测试与下一步

数据迁移位于 `prisma/migrations/20260912220000_project_reports_granular_sanctions_policy/`；纯规则与中文展示标签放 `src/core/governance/` 和 `src/shared/`，服务端放 `src/backend/governance/` 与对应功能目录，页面和表单各自归在 `src/app/` 与 `src/frontend/components/`。逐文件用途见 `docs/architecture/FILE_MAP.md`。交付前验证 Prisma schema、客户端生成、类型检查、生产构建、增量补丁逐字节试应用；本环境无法连接用户 Windows PostgreSQL，真实迁移和多账号回避需本地验收。下一步是公开评论 / 回复与举报复用、项目内部论坛、基于实际案例制定处罚与复核规则；不预设自动封号阈值。
