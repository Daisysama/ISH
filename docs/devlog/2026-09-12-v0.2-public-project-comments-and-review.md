# 2026-09-12 · 项目与动态公开讨论及治理

## 做了什么、为什么改

上一轮项目与动态可发表、举报及下架，但用户不能直接公开讨论或回复。为避免成员讨论与项目内部资料混用，本轮在公开项目和每条已发表动态旁分别建立讨论区。发起人的评论标明「制作人」，其他人可点赞、点踩、仅对自己屏蔽、举报及回复；举报人不能自行裁决，评论作者删除也不会抹掉历史回复与审核原文。

旧命令 `git diff --check` 输出 LF/CRLF 转换预告，不是实际的空白字符错误。尝试给整个仓库强制设定 LF 后发现会反向提示大量既有 CRLF 文件，因此没有修改原有文件换行；`scripts/check-whitespace.ps1` 只关闭 Git 的转换预告，仍让 `diff --check` 检查真正的尾部空格错误。

## 改了什么、思路与边界

1. 新增 `ProjectComment`（项目级或单条动态级、至多一层回复）及事件、个人偏好、举报、申诉各自独立表；作者删除改状态、作者撤销恢复，子回复仍显示在被删评论下，原正文只在作者或授权审查界面可见。评论和举报陈述各自保留快照，撤销不覆盖原事件。
2. 评论仅能写入公开项目及已公开动态；真实服务端 `COMMENTS` 处分拦截评论与回复，恶意表单无法借项目发起人身份绕过。沿用站主维护的安全短语：未命中立即发表；命中 `REVIEW/BLOCK` 进入网站独立审核并提醒符合回避规则的审核员，作者可见等待状态。筛查拒绝后可向另一审核员申诉。限额为每人每日最多 40 条评论及回复、10 条评论举报；并不把命中词条本身当作账号违规。
3. 点赞与点踩互斥且可再次点击取消；点踩会仅对本人折叠评论，切回点赞恢复展开；「仅对我屏蔽」可单独撤销。原有拉黑作者继续折叠作者评论，解除拉黑须去原有拉黑名单，不会误写网站处罚。
4. 举报原文快照和说明只供具 `REPORT_REVIEW` 权限的独立网站管理员。待处理举报可撤回并重新提交；已处理的举报可撤回陈述，但不自动推翻审查结果，应进入可追溯纠错。举报导致下架时自动合并同一评论尚未处理的举报，通知作者、举报人和站主；评论作者可以申诉，原审、举报人、作者及项目发起人回避。站主只能在自身不涉案时填写依据直接纠正，并通知相关方。
5. 当作者主动删除一条正在被举报的评论，举报结论记录为「作者已删除，平台未认定违规」，不遗留不可处理的待办。若作者随后撤销删除，原文只能先回到独立审核队列，旧举报人也必须回避，防止通过删后恢复绕开核查。管理员用户色阶只数当前经过核查的下架，不数尚未核实的举报、撤回陈述或经过申诉恢复的评论。
6. 项目详情和动态列表可进入对应讨论页，分页按顶层评论 30 条；作者删掉内容只显示占位与回复。消息提醒覆盖公开回复、项目新评论、自动筛查结果、举报结论、申诉裁决和站主纠错。

## 约束和后续方向

点踩是个人偏好，不是删除权或违规票选。评论字数为 2～1200，回复暂限一层；帖子内部论坛、私信、投票和对举报滥用的细化处分仍属后续项目。已审结举报的撤回只表示举报人撤回陈述，不代表网站先前的裁决自动撤销。项目内部讨论必须另建受成员权限保护的模型，不借公共评论开内部资料访问。

文件职责逐项登记于 `docs/architecture/FILE_MAP.md`。交付前执行 Prisma schema 校验、迁移 SQL 与模型差异对照、类型检查、生产构建及基于上一轮补丁的无冲突试应用；本环境不连接用户 Windows PostgreSQL，数据库迁移和多角色操作需按安装说明在用户本地核验。下轮先讨论内部论坛/公告及权限，再进入任务、里程碑和投票。
