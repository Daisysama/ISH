# 2026-09-12 · 申诉导航、案件识别与裁决纠错

## 本次目标

用户实测发现：顶部“项目审核”和“申诉审查”会同时高亮；“治理”和“消息”不高亮；申诉卡片的项目、被移出者、操作人与发起人混在一起；申诉跳转项目详情却返回项目审核。另有治理漏洞：管理员处理案件后站主不知情，也缺乏可追溯的纠错操作。本轮按“从哪来，返回就回哪去”修正返回来源，并建立对平台申诉裁决的附理由撤销与独立重审。

## 做了什么

- `GlobalHeader` 和对应四个页面：明确每个顶部入口的 active 值，同一时刻只高亮当前入口；站主查看授权日志时保持治理入口活跃。
- 项目审核页与申诉审查页：移除重复的交叉入口/回链；通过顶部导航切换。
- 申诉卡片：用分列标签标明“项目名称/简介”“被移出 · 申诉人”“执行移出”“项目发起人”“时间”；非公开项目且仅有申诉权限时说明公开简介已提供，避免死链接。
- `src/shared/navigation.ts`、项目详情、本人申诉页和消息打开动作：对来源使用白名单；从申诉详情打开项目时回到具体申诉卡片；从消息进入本人记录返回消息页。
- `src/backend/moderation/actions.ts` 和 `src/backend/removal-reviews/actions.ts`：网站管理员完成初审、修改再审或平台申诉裁决，均在原业务事务里写站主消息；站主如是申诉当事人只收到不含申诉正文的治理提醒。
- `prisma/schema.prisma`、`20260912193000_owner_appeal_corrections`：为申诉事件加入 `REOPENED` 与原裁决/原处理依据/原审查员/时间的独立快照。
- `APPEAL_CORRECTION` 授权及申诉纠错表单：站主或获授两项申诉权限的独立纠错员可填写理由撤销已生效的平台申诉结论，再次排队；当事人、原裁决人、曾参与本案纠错的人不能重审或再次纠错。
- 本人申诉记录和管理员队列显示被撤销的旧裁决及撤销理由；重新裁决生成新通知，旧案原理由及初次裁决不会被历史重写抹去。

## 为什么这样设计

“撤销”仅撤销**平台申诉的现行结论**，保留一个 `REOPENED` 事件中的旧裁决快照，再回到待审状态；现有平台裁决不会自动恢复同行关系，因此没有成员权限需要回滚。重审禁止原裁决人和纠错员再次定案，以免表面换人、实际仍由原人控制。

站主虽然拥有网站治理权，也不能查看或纠正自己作为发起人/申请人的平台案件；这类案件的纠错能力由站主另行授权无利益冲突的人员。站主消息在存在利益冲突时不含申诉陈述。与之不同，已经公开的项目审核若贸然一键撤销，可能破坏版本和用户依赖；站主先收到通知并保留审核事件，项目下架/版本回滚须在后续监管模块中建立明确补偿流程。

## 影响范围

- 前端：顶部导航、申诉卡片、项目与申诉详情返回行为、纠错确认表单。
- 后端：案件裁决/重开权限和事务通知；所有变更由服务端重新校验身份、利益冲突、状态。
- 核心业务：重开平台案后，旧结果不可作为现行结论，旧裁决仍可审计。
- 数据库：枚举追加 `REOPENED`、事件表新增五个快照列；不删除、重写旧事件。
- 部署：需执行一条新 Prisma migration 并重新生成客户端。
- 用户数据/隐私：站主的通知不泄露其自身利益冲突案件的申诉正文；旧案再次裁决生成独立消息。

## 验证

在已交付的站主/消息补丁基线上完成 `npm run db:generate`、Prisma schema validate、`npm run typecheck` 和 `npm run build`；使用 `git apply --check` 与试应用、副本字节对比验证增量补丁。本环境未接入用户的 Windows PostgreSQL，因此本地迁移与三角色浏览器闭环按 `docs/engineering/APPEAL_CORRECTION_CHECKLIST.md` 手动验收。

## 已知问题

管理员完成项目审核时站主会获知，但本轮没有提供一键撤销已上线内容；版本回滚和项目下架必须先有公开内容快照与补偿性事件。站内消息没有邮件/系统推送；历史已经完成的审核不会追溯补发站主提醒。来源白名单覆盖此次用到的入口，后续新增页面须在共享导航映射中登记。

## 后续方向

延续已确定的项目核心路线：Project Updates → 项目动态时间线 → Dashboard“发动态” → Membership 权限面板 → 审核等待时间排序。治理阶段再补下架/恢复与版本回滚、用户封禁、举报拉黑及汇总治理日志。每次实质修改继续同步日志和文件地图。
