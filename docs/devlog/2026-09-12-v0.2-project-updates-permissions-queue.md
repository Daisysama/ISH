# 2026-09-12 · 项目动态、成员授权与统一审核队列

## 为什么做

项目已支持发起、加入、版本再审和同行移出，但公开页面没有持续汇报进展的入口；项目内部活动又包含成员处分与授权理由，不能直接当作对外动态。此前约定的顺序是 Project Updates → 项目公开时间线 → Dashboard“发动态” → Membership 权限面板 → 审核工作台按等待时间排序。这一轮落实上述完整链路。

## 做了什么、改了什么

- 数据库新增 `ProjectUpdate`、`ProjectUpdateEvent`，公开状态为待审/已发布/退回；事件逐次追加提交、通过、退回和站主撤销。成员授权沿用已有 `ProjectMembership.permissions`，项目内部活动新增 `MEMBER_PERMISSIONS_CHANGED`。迁移位于 `prisma/migrations/20260912200000_project_updates`。
- 核心目录分别定义动态字数与退回原因校验、项目成员权限选项、统一等待时间文案。网站 `PROJECT_REVIEW` 与项目 `SUBMIT_UPDATES` 是两套独立权限。
- 项目发起人可为已发布项目提交动态；ACTIVE 同行者须经发起人显式授权。提交和审核时都在后端重新校验身份、项目状态、同行状态与权限。移出成员或撤销授权会阻止其待审内容被通过，先前已公开的署名仍保留。
- Dashboard 提供项目选择与“发动态”入口；项目详情显示最近三条已发布动态，并可进入时间线。作者和发起人可看到该项目的待审/退回原稿及原因，旁人只看到已发布内容；作者可以带入退回原稿重新提交，生成新记录而非覆盖旧裁决。
- 项目审核把首次发布、修改再审、动态审核按统一提交时间混排，默认等待最久优先，可按类型筛选或反向排序。提交/结果/授权变更在原业务事务内写站内消息；项目发起人收到同行者投稿提醒，站主收到管理员裁决提醒。
- 站主可在具体动态审核记录填写原因撤销管理员的发布或退回决定。已公开内容即刻撤下；原结论、原退回原因、审核人 ID、处理时间与纠错依据留在追加式事件中。重开后原审查人及纠错人都不能再次审本条；无独立审核员时提示站主授权。
- 动态编辑器、项目详情、时间线、通知之间使用有限的来源值传递返回目标。用户从 Dashboard 或消息进入的路径会按来源返回，不接受任意跳转网址。

## 思路与边界

`ProjectActivity` 是项目内部敏感操作日志，`ProjectUpdate` 是公开内容，只有通过独立网站审核才进入时间线。项目成员权限由项目发起人配置，网站审核权限由站主配置，任何一方都不能借另一套权限给自己审核。站主纠错是“撤销当前结论并重新排队”，不会抹掉历史，也不能替独立审核员直接发布。项目已退回/下架、作者授权失效时，管理员不得批准此前待审动态。

新动态最多显示最近 50 条，采用普通列表；后续需要分页时可按发布时间与 ID 组合游标，不让无界列表拖慢项目页。已退回原稿生成新的提交与事件；它不重写旧记录，也不会无意公开退回原因。
