# 2026-09-12 · 项目动态筛查、举报、拉黑、账号处分及 ISH 公告

## 为什么改

原有项目动态全部依赖网站人员逐条看稿；公开后缺少用户举报、作者下架申诉，站主也没有可分权的内容规则、账号处分和网站公告入口。随着公开评论和内部社区增加，逐条人工检查不可持续，同时任何自动化措施又必须保留人工纠错和可追溯依据。

## 这次做了什么

- 动态提交时将标题和正文按 Unicode NFKC、大小写及分隔符归一化，对站主 / 受权管理员配置的字面规则匹配；存储命中的规则 ID、规则版本、动作和原文哈希。BLOCK 留在退回列表并允许申请人工复核，REVIEW/CLEAR 都走现有审核流程，不能据此自动封号。规则调整保留变更前后快照、原因、操作者和通知站主。
- 已发布动态具备本人举报和「我的举报」进度；默认独立网站管理员审查，回避举报人、作者和项目发起人。下架不删除原文，作者可提交针对该次下架的申诉；申诉成功转待审，原举报人、作者、发起人和站主能得知结果。并行审核同一内容时锁定动态，避免留下悬空举报。
- 个人拉黑仅折叠自己看到的相关动态及项目卡；可在画像中恢复。平台账号处分单独区分「限制发布」和「限制发布及项目管理」，支持 1/7/30 日，永久处分与管理员账号处分保留站主专权；被处分用户仍可登录、看消息与历史、独立申诉，站主可凭理由撤销管理员的处分。
- ISH 公告分草稿、发布、撤回，管理员须获公告权限且只操作自己草稿，站主可纠错；管理员动作通知站主，站主可选择一次性通知站内所有账号。首页只展示最新公告入口，撤回公告公开留状态说明。
- 导航以一个「治理」入口归并内容规则、举报、公告、处分和独立账号申诉；所有权限在服务器核对，站主可按事项授权网站管理员。各个动作在数据库事务内写事件、状态与站内提醒。

## 思路与权力边界

项目发起人的内部成员管理与网站治理不混同；用户拉黑与网站处分不混同。自动筛查减少有明显命中内容的人工分流成本，但词表不具备理解语境的能力，所以没有把「无命中」直接视为可自动公开。举报核查、下架复核、账号处分申诉与站主纠错都保留原决定和明确的利益冲突回避。账号限制控制服务端写入口，不能靠前端隐藏按钮实现。

## 涉及的区域

数据与迁移：`prisma/schema.prisma` 和 `20260912210000_content_screening_reports/migration.sql`。纯规则：`src/core/governance/screening.ts` 及权限表。服务端按事项位于 `src/backend/governance/`、`announcements/`、`blocks/`、`sanctions/` 和认证写入门禁；前端分功能位于 `src/frontend/components/` 与对应的 `src/app/` 页面。所有新增文件的职责见 `docs/architecture/FILE_MAP.md`。

## 核验与限制

Prisma schema 验证、TypeScript 类型检查、Next.js 生产构建、差量补丁试应用以及核心文字归一化的边界测试在交付前执行。此环境没有连到用户 Windows 本地 PostgreSQL；迁移执行、具体权限账号间的完整交互需在本地按 PowerShell 手册验收。该版规则覆盖项目动态；项目、项目修改、项目回应仍按原审核路径，评论和内部论坛还没有数据模型。个人拉黑仅折叠当前可见的项目与动态，不撤销旧权益或网站审核权限。公告批量通知在站主主动选中时同步写入，用户规模扩大后应改为事务性队列分批投递。
