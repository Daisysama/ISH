# 2026-09-12 · 移出可见性与独立复核

开发者：Codex；开发基线：Lysander 提供的 FromISH 本地最新项目。

## 本次目标

将移出同行者从“突然消失”变为本人可见、可解释、可复核的历史事件。发起人纠正误操作与网站管理员审查滥权须分设通道。

## 做了什么

- 将项目详情的“管理/查看同行者”入口放进“同行者 X 位”信息格。
- 我的项目增加历史项目，显示已退出/被移出；被移出时在页面上方提示，并保留时间、理由、操作人及核查入口。
- 非公开项目被移出的用户只能访问自己的最小移出回执，不再访问项目正文、团队页、申请制群聊。
- 新增每次移出的不可覆盖回执；migration 对现存 REMOVED 成员补建回执，新的移出动作与回执在同一事务写入。发起人后来即使恢复同行，用户仍可就该次移出向平台申诉。
- 每次回执可分别向发起人、网站管理员提交申请，申请又各自固化回执的原始原因/时间/操作人显示名。两条通道互不覆盖。
- 发起人可在团队页核查、恢复或主动纠正误操作；只看发起人通道，不看平台申诉说明。
- 网站管理员在独立后台审理平台申诉；项目发起人或申诉人即使拥有网站管理员资格，也不得审理自己的案件。
- 审理结论与理由均入库并追加事件；平台可说明“未发现违规 / 官方纠正说明 / 行为不当待进一步处置”，不会默认强迫私人协作继续。
- 原始移除/恢复仍由项目内部活动留痕，申请事件另行追加；恢复不抹去此前移出事实，发起人恢复也不会自动终止平台调查。

## 为什么这样设计

关系终止不等于劳动、合同、贡献或申诉事实消失。发起人能决定是否继续协作，但不能独占对自己行为的审查；平台可纠正记录和认定滥权，却不能机械地把两人强行重新编成团队。申请内容只给所选的受理方，减少报复和隐私扩散。

## 影响范围

- 前端：项目详情、我的项目、项目团队、本人申请页、网站管理员申诉页。
- 后端：服务端身份/成员状态检查、申请人快照、分角色裁决、并发条件更新和事务活动记录。
- 数据库：一个追加 migration；新建移出回执、复核和事件三表，给项目内部活动增加恢复类型。
- 权限：历史关系仅授予本人查看回执及申诉状态，不恢复任何成员功能。网站管理员沿用当前 `ADMIN_EMAILS` 授权；后续换 RBAC 时需迁移这一审理权限。

## 验证

- 本地执行 `npm run db:generate`、`npx prisma validate`、`npm run typecheck`、`npm run build`，通过。
- 未连接用户实际数据库，未在生产执行 migration。Windows 本地按现有 `scripts/migrate-local.ps1` 迁移后仍需用双账号验证：发起人移出 → 成员历史与回执 → 发起人申请/恢复 → 网站管理员独立申诉/裁决 → 原团队权限拒绝。

## 已知问题

- 目前没有独立站内通知收件箱或邮件；我的项目首页用醒目提示及历史区保证状态可见，也未做“已读”状态。
- 平台“行为不当”仅形成可追溯认定，不自动冻结收益、判定合同或执行账号处分；这些属于后续治理模块。
- 当前项目/成员关系沿用既有级联删除约定。真正启用项目删除功能前，应先定义申诉、贡献和审计记录的持久保存与脱敏规则。
- 如果当前唯一网站管理员本身是项目发起人，利益冲突规则会阻止其自审；应增加一名独立管理员后再受理，不可绕过。

## 后续方向

站内通知及已读状态、证据附件与隐私隔离、平台二审/复议、正式管理员 RBAC 与回避指派、贡献及收益争议保全、较长历史列表分页。
