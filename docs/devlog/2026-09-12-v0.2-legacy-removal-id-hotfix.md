# 2026-09-12 · 旧移出回执无法提交申诉

开发者：Codex；基线：移出申诉表单与提醒补丁。

## 本次目标

修复旧移出成员在申诉表单填写合法内容后，始终收到“申请记录已失效”的问题。

## 做了什么、改了什么

- 排查到 `20260912180000_project_removal_reviews` 的回填 SQL 用 `md5(membershipId + leftAt)` 生成 32 位十六进制回执 ID，而申诉提交的服务端校验仅接受 UUID。新移出由 Prisma 自动生成 UUID，因而原代码漏掉了迁移前已移出的成员。
- 申诉提交的 **removalId** 校验改为接受 UUID 或精确 32 位十六进制；其他 ID 的 UUID 校验保持不变。
- 对无法识别的回执编号与无效申诉通道分别返回具体错误，不再误称申请记录失效。
- 更新文件职责地图。

## 为什么这样设计

已应用的 migration 和已有回执属于历史事实，不应为了前端校验重写它们的主键。格式校验只限制输入形状；实际创建申请前仍查询回执、核对它所属成员的 `userId` 与当前登录用户一致。选择兼容两类已存在 ID，不扩大其他资源 ID 的接受范围。

## 影响范围与验证

- 后端：仅申诉提交动作的回执 ID 校验与错误文案；前端、数据库表、权限和审查事件结构不变。
- 本地复现：旧 `md5(...)` 结果是 32 位，旧 `z.string().uuid()` 对其返回 `false`；修复后分别验证旧格式、新 UUID 通过，非预期字符串被拒绝。
- 执行 `npm run typecheck` 和 `npm run build`；用户 Windows 本地仍须用旧移出记录、最新移出记录各提交一次申诉，并核对非本人无法提交。

## 已知问题与后续方向

无法连接用户本地数据库复测实际历史回执；数据库关联与归属检查继续提供最终保护。下一轮应为移出前后迁移的申诉路径增加覆盖历史 ID 的自动化集成测试；之后延续持续监管与管理员治理的既定路线。
