# Devlog · Member Lifecycle & Project Activity

日期：2026-09-12

## 做了什么

1. `ProjectMembership` 不再只表示 ACTIVE：主动退出与被移除会保留 `LEFT / REMOVED` 历史状态、时间与理由。
2. 新增 `ProjectActivity` 内部活动流，第一阶段记录成员加入、主动退出、被移除。
3. 接受响应并建立 / 恢复 membership 时，在同一事务里记录 `MEMBER_JOINED`。
4. 项目发起人可以在“我的项目 → 同行者”进入团队页，移除成员时必须填写 5–500 字理由。
5. ACTIVE 同行者可以在团队页主动退出，也必须留下简短说明。
6. 移除 / 退出会立即清空成员权限；申请制群聊等能力继续只认 ACTIVE membership。
7. 被移除者在项目详情能看到自己的移除理由与操作人，但完整内部活动流只向项目发起人与当前 ACTIVE 同行者开放。
8. PC 与移动端都提供可触达的团队入口；手机端高影响操作按钮使用整行点击区域。

## 为什么这样做

成员关系不能通过 `DELETE` 静默消失。项目协作里最不愉快的动作也需要说明、边界和可追溯性。

“项目动态”和“项目内部活动”必须分离：前者以后是面对羊群的公开成长轨迹；后者承载成员加入 / 退出 / 移除、权限变化等内部协作事实。完整移除理由不应被系统自动公开，避免把内部冲突变成公开羞辱或隐私泄露。

## 安全与一致性

- 移除和退出都使用数据库事务：成员状态变化与活动留痕要么一起成功，要么一起回滚。
- `REMOVED` 成员当前不能直接再次响应，避免刚被移除后立即反复申请造成骚扰。
- 历史 `ProjectResponse = APPROVED` 不继续提供成员权限；最终凭证仍然只有 ACTIVE membership。
- 重新接受曾主动退出的成员时，旧 departure 信息会清空，并生成新的加入活动。

## 下一步

下一模块建立细粒度项目权限：项目资料、动态创建 / 修改 / 提交、回应处理、成员管理。权限变化也会复用 `ProjectActivity` 留痕，而不是另造一套历史系统。
