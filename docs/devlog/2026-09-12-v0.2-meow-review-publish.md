# 2026-09-12 · v0.2「咩 → 项目主页 → 审核 → 发布」

## 本次目标

让 ISH 从“只有账号系统的公网 Alpha”第一次进入真实业务闭环：

> 咩 → 项目主页 → 人工审核 → 公开发布

本轮只解决“一个项目如何被提出、如何在公开前被治理、如何正式出现于公共页面”。
不同时加入私信、项目申请、玩家反馈、支付等功能，避免一次扩张过多边界。

## 做了什么

### 1. 建立 Project 领域模型

新增：

- `Project`
- `ProjectStatus`：`PENDING / PUBLISHED / REJECTED`
- `ProjectModerationEvent`
- `ModerationAction`：`APPROVED / REJECTED`

项目提交后默认 `PENDING`，不会直接公开。

审核事件采用追加式记录，不只保存项目当前状态，以便未来追溯谁做了什么治理动作。

### 2. 建立「咩」提交入口

新增 `/meow/new`：

- 项目标题
- 一句话介绍
- 项目说明

校验规则集中在 `src/core/meow/project.ts`，不散落在页面和数据库层。

提交成功后创建 PENDING 项目，并跳转到创作者自己的非公开项目页。

### 3. 建立项目主页与访问边界

新增：

- `/projects`：只展示 PUBLISHED 项目；
- `/projects/[id]`：项目主页。

访问规则：

- PUBLISHED：任何访客可看；
- PENDING / REJECTED：只有创作者本人和管理员可看；
- 无权限用户返回 404，不泄露非公开项目是否存在。

### 4. 建立最小管理员审核后台

新增 `/admin/moderation`：

- 只列 PENDING 项目；
- 可以“审核通过并发布”；
- 可以“退回修改”；
- 退回必须填写明确原因。

状态修改和审核事件写入使用 Prisma transaction，避免只改状态但没有留痕，或只留痕但状态没改的半完成状态。

### 5. v0.2 Alpha 管理员授权

当前管理员数量极少，因此暂时通过服务器环境变量：

`ADMIN_EMAILS`

进行授权。

这样避免把管理员邮箱硬编码进仓库，也不为了单管理员 Alpha 过早设计完整 RBAC。

已知代价：

- 权限修改需要改环境变量 / 重启应用；
- 不适合未来多人、多角色治理。

后续成员规模扩大后，应迁移到数据库 RBAC / permission 模型。

### 6. Dashboard 与公开入口

Dashboard 从占位页升级为：

- 我的项目；
- 审核状态；
- 退回原因；
- “咩一个项目”入口。

根路径调整为：

- 已登录 → `/dashboard`
- 未登录 → `/projects`

使 `fromish.com` 可以直接作为公开宣传入口，而不是强制访客先登录。

### 7. 从 db push 正式切换到 Prisma Migration

v0.1.x 生产库最初通过 `prisma db push` 建立，因此本轮建立：

- `20260912000000_v0_1_baseline`
- `20260912053000_add_meow_projects`

对于已经存在 `users` 表的旧数据库：

先把 baseline 标记为 applied，再执行 `migrate deploy`。

新空数据库直接执行 migrations。

本地增加 `scripts/migrate-local.ps1` 自动兼容 v0.1.x 开发库。
生产 baseline 仍要求：先备份、人工核对、再执行，不能自动化冒险。

## 为什么这样设计

### 为什么“咩”不能提交后直接公开

ISH 后续允许普通用户创建项目和公开内容。冷启动阶段内容质量、违法违规、广告、侵权和纯幻想项目都会直接影响平台可信度。

因此 Alpha 采用最简单但最可控的方式：

> 所有项目先审后发。

这不是永久产品形态，但非常适合当前只有少量内容和单管理员的阶段。

### 为什么先不做 Draft / 修改后重新送审

完整内容系统通常需要：

`DRAFT → PENDING → PUBLISHED → EDIT_PENDING / ARCHIVED ...`

但第一版直接建立完整状态机，会把编辑冲突、审核版本快照、公开内容更新边界一次带进来。

本轮只验证最短闭环，项目修改 / 重新送审作为后续独立设计。

### 为什么管理员暂时不用数据库 Role

现在只有极少管理员，引入 Role/RBAC 会额外增加：

- 用户表 migration；
- 管理员提升工具；
- 权限管理页面；
- 权限审计模型。

v0.2 先用服务器环境变量完成最低成本、服务端可信的授权；当实际出现多管理员需求再迁移。

### 为什么审核动作单独建事件表

只在 Project 上保存 `status/rejectionReason` 会丢失历史。

ISH 的治理原则要求重要治理动作可追溯，因此从第一版就追加 `ProjectModerationEvent`。

## 安全与隐私边界

- 非公开项目权限由服务端检查，不依赖“前端不显示链接”；
- React 直接输出纯文本，不接受用户 HTML；
- 管理员名单只从服务端环境变量读取；
- 审核 Server Action 再次检查管理员权限；
- 项目 UUID 不是权限控制手段，只是标识符；
- 本轮不接受可执行文件上传；
- 本轮不加入站内私信；
- 本轮不处理支付或资金。

## 数据库影响

新增：

- enums：`ProjectStatus`、`ModerationAction`
- tables：`projects`、`project_moderation_events`
- indexes 与 foreign keys

不删除或重写既有用户数据。

## 本地环境搭建热修：Windows PowerShell 5.1 编码与错误传播

在 Windows PowerShell 5.1 首次执行 `scripts/setup.ps1` 时发现两个工程问题：

1. `scripts/migrate-local.ps1` 为 UTF-8 无 BOM，Windows PowerShell 5.1 按本地 ANSI 代码页解析中文，造成中文字符串乱码，并进一步触发字符串终止符 / 语句块解析错误；
2. `setup.ps1` 调用 PowerShell 子脚本后只检查 `$LASTEXITCODE`。当子脚本在 PowerShell 解析阶段失败时，`$LASTEXITCODE` 可能仍保留前一个原生命令的成功值，导致 setup 错误地继续输出“完成 / 搭建完成”。

### 修复

- 将 `scripts/migrate-local.ps1` 保存为 UTF-8 with BOM，确保 Windows PowerShell 5.1 能稳定解析中文脚本；
- `setup.ps1` 在调用 migration 子脚本后同时检查 PowerShell 的 `$?` 与 `$LASTEXITCODE`；
- migration 子脚本解析或运行失败时，setup 立即失败，不再输出虚假的“搭建完成”。

### 影响

本热修不修改数据库 Schema，不执行额外数据库变更，也不影响生产环境。
已经创建的本地 `.pgdata` 与 `.env` 可以保留；修复脚本后重新执行本地 migration 即可继续。

## 本地环境搭建热修：Schema 更新后 Prisma Client 仍为旧版本

在 v0.2 数据库 migration 成功后执行 `npm run typecheck` 时发现，
TypeScript 仍提示 `PrismaClient` 不存在 `project` / `projectModerationEvent` 属性。

### 原因

本地 `node_modules` 已存在，因此 `setup.ps1` 跳过了 `npm ci`。
虽然数据库 migration 已经成功应用，但 Prisma Client 是根据旧版 v0.1 schema 生成的。

数据库 migration 与 Prisma Client Generation 是两个独立步骤：

- migration 更新数据库结构；
- `prisma generate` 更新 TypeScript / JavaScript 客户端代码和类型。

仅完成 migration 不会自动保证已有开发环境中的 Prisma Client 已同步。

由此产生的 `project` 属性缺失，以及页面中 `map` 回调参数的 implicit `any`
均属于旧 Prisma Client 类型造成的连锁错误，不应通过手工补 `any` 掩盖。

### 修复

`setup.ps1` 在完成本地 migration 后，无论 `node_modules` 是否已经存在，
都显式执行：

`npm run db:generate`

确保 Prisma Client 始终与当前 `prisma/schema.prisma` 一致。

### 当前环境恢复方式

对于已经完成 v0.2 migration 的本地环境，不需要重建数据库，也不需要重新执行 migration。
只需运行：

`npm run db:generate`

随后重新执行：

`npm run typecheck`
`npm run build`

### 设计原则

不把数据库 Schema 同步、数据库 Migration、Prisma Client Generation 混为一个动作。
每一步职责独立，但本地一键搭建脚本必须按正确顺序编排，避免开发者依赖隐含知识。
