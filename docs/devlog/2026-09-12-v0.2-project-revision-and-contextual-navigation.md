# Devlog · Project Revision & Contextual Navigation

日期：2026-09-12

## 做了什么

1. 为已发布项目建立 `ProjectRevision` 修改草稿。
2. 创作者可以在“我的项目”卡片右侧直接进入“修改 / 查看修改 / 继续修改”。
3. 修改稿审核期间，公开 `Project` 保持原版本；审核通过时在事务中一次性切换为新版。
4. 管理员审核页同时展示“首次公开”与“修改再审”，修改再审只突出发生变化的字段。
5. 修改被退回后保留同一版本草稿，创作者可以继续修改并重新提交。
6. 项目详情返回路径改为显式、白名单化的来源语义：羊群广场 / 我的项目 / 回应中心 / 审核 / 首页 / 个人资料。
7. “咩一个”和“审核”作为一级页面，移除伪造的 `← 我的项目` breadcrumb。
8. Dashboard 项目操作同时按 PC 与移动端设计；手机端“查看 / 修改”落到卡片底部大按钮区域。
9. 申请制群聊从“未来能力”正式开放：只有 ACTIVE 项目同行者可以解锁申请制群聊信息。

## 为什么这样改

直接修改线上 `Project` 会产生一个治理漏洞：审核中的内容已经对外生效，管理员无法保证公开版本始终是被审核过的版本。

因此修改采用双版本模型：

`公开 V1 → 编辑 V2 草稿 → 修改再审 → V1 持续公开 → 审核通过 → 原子切换 V2`

退回时只改变 revision 状态，不触碰线上项目。

导航上，`history.back()` 不足以表达产品语义：刷新、新标签页、分享链接都会让浏览器历史不可预测。因此详情页使用受控来源标识；一级页面则依赖稳定 Global Header，不制造不存在的上下级关系。

## 关键权衡

- Alpha 阶段同一项目只允许一份 `PENDING` 修改稿，避免版本竞态。
- 新同行者仍然默认只读；Project Revision 目前只有项目发起人可以提交。
- Revision 使用结构化字段快照，而不是直接保存任意 JSON，便于 Prisma 类型约束、审核 Diff 和未来迁移。
- 已通过 / 已退回的 revision 与审核事件都保留，不做硬删除。
- 移动端不复刻 PC 三列布局；项目卡操作在窄屏下改为底部按钮区。

## 后续方向

- 在 Project Membership 上增加显式权限授予后，再允许被授权成员提交修改草稿。
- 治理后台扩展为待审核 / 已发布 / 待修改 / 已下架 / 全部，并加入下架、恢复、举报与统一治理日志。
- 版本历史页可展示 V1/V2/V3 差异与审核记录。
- 羊群广场未来可进一步保留筛选条件的精确返回位置，而不仅是返回广场入口。
