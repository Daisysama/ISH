# v0.2 Discovery Filter & Sticky Return

## 做了什么

- 羊群广场的阶段、目的、项目标签由单选改为多选；排序方式保持单选。
- 同组筛选采用 OR，不同组采用 AND。
- 新增紧凑的复选筛选浮层，避免原生单选下拉限制真实项目组合。
- 项目详情新增吸附式返回条，滚动到底部仍可返回羊群广场或我的项目。
- 首页文案更新为“一声小小的咩，也许就是下一部神作的伊始。”

## 为什么改

真实项目往往同时处于多个用户关心的分类交集，例如“已有 Demo + 邀请试玩 + 视觉小说”。单选筛选会迫使用户丢失条件。
同时，长项目详情页如果只在顶部提供返回入口，会让用户阅读完成后找不到站内出口。

## 取舍

本轮不加入复杂的查询构建器；仅采用易理解的“组内 OR / 组间 AND”。
返回条使用明确站内链接而不是仅调用浏览器后退，以兼容搜索引擎和外部分享直达项目页的场景。

## 筛选菜单交互与对齐修正

现场验收发现两个系统性易用性问题：

- 同一时间可以打开多个筛选浮层，导致菜单互相覆盖，用户必须逐个手动关闭。
- 排序控件的辅助标签未被视觉隐藏，导致筛选栏出现纵向错位；各操作控件高度也不完全一致。

本轮修正：

- 顶层筛选菜单加入同组互斥行为：打开新的“阶段 / 目的 / 标签”菜单时，已打开的同级菜单自动关闭。
- 补齐通用 `sr-only` 无障碍样式，保留屏幕阅读器语义但不占据视觉布局。
- 筛选触发器、排序框、“筛一筛”和“清空”统一到同一视觉基线与高度。

产品规则：同级临时浮层默认互斥；同一操作栏中的同级控件应共享稳定的视觉基线，不能让功能增加破坏页面秩序。

## 清空、排序菜单与收藏排序修正

继续现场验收后发现：

- 多选项使用非受控 checkbox 时，点击“清空”虽然 URL 回到默认状态，当前组件里的旧勾选仍可能保留，造成“看起来没有清空”的错觉。
- 排序仍使用浏览器原生 `select`，既没有和其他临时浮层互斥，视觉语言也不统一。
- 用户已经需要按“感兴趣 / 收藏 / 发布时间 / 猜您喜欢”浏览项目，因此排序能力需要和发现系统一起收口。

本轮修改：

- DiscoveryFilter 改为受控客户端交互；“清空”会立即清空阶段、目的、标签、排序方向和所有可见勾选，再回到默认发现状态。
- 阶段、目的、标签、排序方式、正序 / 倒序全部进入同一个 `openMenu` 状态，同一时间只能存在一个临时浮层；点击空白处或 Escape 也会关闭。
- 排序增加“猜您喜欢 / 发布时间 / 感兴趣最多 / 收藏最多”，并提供正序与倒序。
- 新增私人收藏关系和收藏入口；单个用户收藏行为不公开展示，但聚合收藏数可以作为排序依据。
- “猜您喜欢”继续优先使用用户明确喜欢标签的重合度，弱推断只做辅助。

产品规则：清空必须真正回到默认状态；同级临时浮层使用同一套交互语言；私人行为可以在保护个体隐私的前提下形成匿名聚合排序信号。

## B.2a-2：咩！（响应）

### 做了什么

- 把“感兴趣”和“行动响应”彻底区分：前者是私人推荐信号，后者会真实送达项目创作者。
- 在公开项目详情加入“咩！我想响应”。响应者可以选择自己想以什么方式参与，并补一句简短说明。
- 创作者可以在“回应我的咩”里查看响应者的自述能力、项目经历与作品链接，并选择“接受同行 / 婉拒”。
- `申请通过后展示` 的群聊信息正式启用：只有创作者接受响应后，该响应者才能看到对应群聊方式。
- 响应者可以在创作者处理前撤回；被婉拒或主动撤回后，可以在情况变化时重新响应。
- 登录 / 注册支持安全的站内 `next` 返回路径：用户从项目页点击响应后登录，不再被强制丢回 Dashboard。

### 为什么这样做

“感兴趣”只是“这个项目合我胃口”，不能被误解为“我要加入”。FromISH 需要一个明确、低门槛但有行动含义的第二层动作，让创作者知道谁真的愿意走近一步。

同时，保密群聊不能因为用户自称“程序 / 美工”就直接解锁。用户画像是自述资料，不是身份认证；最终是否接纳同行者应由项目创作者决定。

### 产品边界

- 响应者资料明确标注“用户自述，未经 ISH 能力认证”。
- 创作者决定是否接受同行；ISH 不替创作者做最终人员选择。
- `PRIVATE` 群聊即使接受响应也不自动公开；`PUBLIC` 群聊继续公开；只有 `APPROVAL_REQUIRED` 与接受响应形成自动解锁关系。
- 当前阶段不把“咩！（响应）”做成公开评论，也不公开响应数量，避免把协作申请变成社交热度竞赛。
