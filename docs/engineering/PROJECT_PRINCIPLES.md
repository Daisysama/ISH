# ISH 工程根本原则

以下规则适用于 ISH 的所有开发者、代码生成工具和后续维护者。

## 原则一：任何实质性修改必须可追溯

每次对功能、架构、数据库、安全、部署或重要 UI 做出实质性修改，都必须新增开发日志。

开发日志至少回答：

1. 做了什么；
2. 改了什么；
3. 为什么改；
4. 采用了什么设计思路、方案与权衡；
5. 影响哪些模块或数据；
6. 如何验证；
7. 当前有哪些已知问题；
8. 下一步可能怎样继续。

日志只新增，不覆写历史。目标是让下一位开发者不用猜测前人的意图即可继续工作。

## 原则二：所有文件必须有明确职责与归属

新增文件必须进入与其职责对应的目录，不把业务代码随手堆在根目录或路由目录。

项目当前的主要职责层：

- `src/app/`：Next.js 路由与页面入口；
- `src/frontend/`：前端组件和浏览器交互；
- `src/backend/`：鉴权、服务端业务、数据库访问；
- `src/core/`：与 UI、数据库和框架解耦的核心业务规则；
- `src/shared/`：前后端共享的类型、schema、常量和纯工具；
- `prisma/`：数据库 schema、migration 与数据库说明；
- `deploy/`：生产部署；
- `scripts/`：本地开发与运维脚本；
- `docs/`：架构、规范、决策和开发日志。

任何重要目录都必须有文档说明“这里应该放什么、不能放什么”。

## 原则三：先定义边界，再增加功能；先保证可回退，再上线

- 路由层尽量薄，不把大量业务逻辑写在 `src/app/`；
- 数据库结构进入真实数据阶段后必须使用可审计 migration；
- 生产环境修改必须来自版本控制，不在服务器上长期保留手工补丁；
- 每次生产发布应能对应到明确的 commit/tag；
- 高风险修改必须写验证与回退说明。

## 代码审查时的最低问题

提交前至少确认：

- 这次修改有没有开发日志？
- 新文件为什么放在这里？
- 是否出现跨层职责混乱？
- 是否引入数据库兼容风险？
- 是否改变用户数据或权限？
- 是否有验证方法？
- 下一位开发者是否能够从文档理解这次改动？
