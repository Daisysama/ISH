# FromISH 内容治理与社区建设顺序

## 已具备的基础

项目成员关系、我发起的 / 我同行的、同行者列表、已发布项目修改再审、站主与网站管理员分权、独立的同行移出申诉和站内消息已建立。项目动态现在也具备作者授权、人工审核、事件留痕与站主纠错。

现有治理已覆盖**项目公开动态**的规则筛查和举报，也能举报已公开项目，项目及动态各自保留原始快照、独立下架复核与站主纠错。个人拉黑只影响本人看到的内容，不代替网站处分。账号处分按评论、项目和动态、响应及最高级全站停用分开记录；全站停用仍保留本人处分和申诉入口。ISH 公告单独授权，管理员操作会提醒站主。

## 内容处理原则

1. 规则包括短语、`REVIEW` / `BLOCK`、版本、操作者、理由和快照。仅匹配文字，不运行用户输入的正则。无规则命中只表示“未命中当前规则”，**不能视为已人工确认安全**。默认仍需审核；站主可以独自开启「未命中直接公开」，须记录原因并确认误判风险，公开后仍可举报与复核。
2. `BLOCK` 暂缓发布、保留原稿与命中规则快照，作者可以申请人工复核；规则本身不能自动封号。`REVIEW` 进入人工审核。误判要能通过修订规则、重新审核和审计记录纠正。
3. 举报与审核相互独立：项目发起人、动态作者和举报人不能裁决本案；下架后撤出公开列表，原文和理由保存在受限记录。动态作者申诉时，原审核人、举报人和项目发起人回避。恢复先回到待审，不直接重新公开。
4. 站主撤销网站管理员处理必须填写原因、通知相关人员并保留原决定；如站主有利益冲突，需要授权不涉案的网站管理员处理，不让案件假装已解决。
5. 处分独立限制评论、咩项目和动态、响应；此前的泛用处分原样保留。全站停用仅站主可永久作出，但必须保留本人处分、消息及独立申诉入口，以便纠错，不删除项目或劳动历史。有限期的单项限制过期后停止阻拦写入，旧记录仍可见。具体过错与时长对应关系以后另定管理细则。
6. 公告按草稿、发布、撤回流转；撤回留公开状态说明，不悄悄改写旧版。全员逐人站内通知由站主显式选择，避免每次小公告打扰全部用户。

## 公开讨论已落地（本轮）

项目与单条公开动态分别拥有评论区；每条评论至多回复一层，制作人回复有标识。评论和回复共享点赞、点踩与私有屏蔽：点踩只折叠本人视图，不替平台判定违规；点赞、点踩和屏蔽可分别撤销。作者删除仅隐藏展示，回复链以提示占位，作者可撤销删除。筛查未命中即发表、命中暂缓并交独立管理员复核；不会仅凭词条自动封号。评论举报可在审核前撤回，已审结的举报仍可撤回原陈述，但独立裁决需另外纠错才会改变。评论经网站下架时作者可申诉，原审核人、举报人、项目发起人必须回避，站主与案子有关也不能自行纠正。原文、原裁决、站主纠错与复核理由分别留痕。

## 后续开发顺序

1. 扩展到**项目内部社区**：主题、回复、项目公告与项目成员权限；内部发帖仍受网站封禁与规则约束，退出成员看不到新内部内容但保留本人可取回的历史权益材料。
2. 把评论规则命中率、审核耗时、申诉纠错率和误判案例纳入治理工作台。评论尚未设计单独的规则词典；现阶段沿用网站筛查短语，人工复核流程监测误判。
3. 随社区规模增长加入管理员队列分配、批量处理审计、更细的反刷屏和举报滥用处置、评论通知降噪，以及基于实际案例制定处分尺度。评论目前每页展示 30 条顶层讨论；长回复链以后可分页。
4. 项目任务、里程碑及投票排在社区权限与治理之后，以免项目内部劳动与纠纷缺少留痕。

视觉上以明确状态、安静提示、可发现的恢复入口代替令人恐慌的突然消失；可回退页面遵循“从哪里来，返回哪里”。任何新增文件在文件地图写清职责，任何实质功能修改追加开发日志。
