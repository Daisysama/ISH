# FromISH 发现与访问原则

## 1. 低下限，高上限

普通创作者应当能在几分钟内完成一声“咩”。系统内部可以复杂，但不能把权限模型、推荐模型直接丢给用户配置。

项目发现围绕四个问题组织：

1. 咩咩啊？——项目类型。
2. 长到哪儿啦？——项目成熟度。
3. 这声咩想干嘛？——寻找同行、试玩、反馈、宣传或分享。
4. 主要想让谁听见？——大家、同行或玩家。

其中“主要想让谁听见”当前用于推荐和筛选，不是强制访问控制。

## 2. 群聊开放与项目发现分离

群聊可能是宣传入口，也可能包含保密协作信息，因此由创作者选择开放方式：

- PUBLIC：公开展示；适合玩家群、试玩和宣传。
- APPROVAL_REQUIRED：响应被创作者接受、建立 ACTIVE 同行关系后展示。
- PRIVATE：暂不对外展示。

ISH 是否加入群聊必须由创作者主动勾选同意。

## 3. 用户画像自愿填写

注册保持低门槛。技能、兴趣、雷点、经历和作品链接均为可选信息。

用户自述的技能与经历默认不构成 ISH 认证。兴趣与雷点用于推荐权重；雷点不会禁止用户主动搜索或访问内容。

## 4. 推荐先透明，再复杂

Alpha 推荐基于可解释规则：兴趣匹配、技能需求匹配、目标受众与发布时间。

不使用无法解释的黑箱排序，不伪造推荐精度。

## 5. 公开内容与搜索引擎

只有正式发布的公开项目进入 Sitemap 和搜索索引。登录、注册、工作台、发布页、用户画像、审核后台和未来治理后台均 noindex。

SEO 优化不得以堆砌关键词或制造无效页面为代价。

## 筛选不是二选一

筛选应该帮助用户缩小世界，而不是逼用户只选一种可能。

- 阶段、目的、标签、未来的技能需求都支持多选。
- 同一筛选组内部使用 OR：例如“已有 Demo / 正在开发”表示命中任意一种即可。
- 不同筛选组之间使用 AND：例如“Demo 或开发中”并且“试玩或找同行”。
- 排序方式始终单选；有足够画像数据时可使用“为您推荐”。

## 长页面不能把出口留在身后

项目详情等明显存在纵向滚动的页面，返回上级页面的路径必须持续可访问。
项目详情使用吸附式“← 羊群广场 / ← 我的项目”返回条，不要求用户滚回顶部才能离开。
明确的站内返回链接优先于把 `history.back()` 当唯一出口，因为用户可能从搜索或分享链接直接进入。

## 感兴趣不等于响应

- “感兴趣”只是用户自己的推荐信号，不应该打扰创作者。
- “咩！（响应）”才表示用户愿意走近一步，并会真实送达创作者。
- 用户画像只帮助创作者理解响应者自述的能力与经历，不构成 ISH 认证。
- 对申请制群聊，是否接纳响应者由创作者决定；平台不因为标签匹配就自动泄露群聊信息。
